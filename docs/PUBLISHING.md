# Публикация отдельного проекта на GitHub Pages

Каждая папка `hw-*` — корень **самостоятельного репозитория**. Нельзя загружать все четыре папки в один репозиторий и ожидать, что четыре корневых workflow будут запущены: GitHub видит `.github/workflows` только в корне конкретного репозитория.

## Первый запуск и проверка

Нужны Node.js 24 (рекомендуется), npm, Git и доступ к npm registry. Откройте терминал в папке нужного проекта:

```bash
npm install
npm run check
npx playwright install chromium
npm run test:e2e
```

Первый `npm install` создаёт `package-lock.json`. Добавьте его в Git. После этого для повторяемой установки используйте `npm ci`. В архиве нет lockfile: зависимости не удалось разрешить через npm в изолированной среде, поэтому неподтверждённый lockfile не создавался.

Браузерные тесты сами соберут production-версию и запустят preview под `/repository-check/`. Порт 4173 должен быть свободен. В Linux при отсутствии системных библиотек браузера выполните `npx playwright install --with-deps chromium`; эта команда может запросить административные права.

## Создание и заполнение репозитория

Создайте на GitHub **пустой** репозиторий. Для обычного бесплатного размещения используйте публичный репозиторий. Не создавайте в нём заранее README, `.gitignore` или license, чтобы начальные истории не конфликтовали. Имена репозиториев могут отличаться от имён папок.

Команды ниже выполняются из папки одного проекта. Замените `USERNAME` и `REPOSITORY` своими значениями:

```bash
git init -b main
git add .
git commit -m "Initial project"
git remote add origin https://github.com/USERNAME/REPOSITORY.git
git push -u origin main
```

При запросе Git укажите своё имя и email через `git config user.name "..."` и `git config user.email "..."`. Для HTTPS войдите через поддерживаемый GitHub менеджер учётных данных/браузер или используйте персональный токен. Не вставляйте токен в исходный код и README.

Повторите процесс отдельно для каждой из четырёх папок. Не запускайте `git init` в общей папке архива. Для уже непустого репозитория сначала клонируйте его и перенесите в него содержимое нужного проекта; не используйте force push для обхода конфликта историй.

## Включение Pages

В репозитории откройте **Settings → Pages → Build and deployment → Source → GitHub Actions**. Затем откройте **Actions → Check and deploy to GitHub Pages** и запустите **Run workflow** для `main`, либо сделайте следующий push. Если первая попытка была до включения Pages, после настройки повторите workflow.

Workflow сначала устанавливает зависимости, запускает ESLint, unit-тесты и E2E. При ошибке публикация не выполняется. После успешных проверок происходит отдельная сборка с реальным базовым путём Pages и публикация `dist`.

`actions/configure-pages` возвращает `base_path`; он передаётся как `PAGES_BASE_PATH`. `vite.config.js` получает `/имя-репозитория/` для project Pages или `/` для пользовательского сайта/корневого домена. Вручную прописывать имя репозитория в исходном коде не нужно.

Права заданы в workflow: чтение кода и Pages metadata для сборки; `pages: write` и `id-token: write` для публикации в окружение `github-pages`. Секретный PAT для штатной публикации не нужен, используется встроенный GitHub token. Организационные правила доступа/подтверждения окружения могут потребовать действий владельца.

Ожидаемый адрес обычного project Pages:

```text
https://USERNAME.github.io/REPOSITORY/
```

Точный опубликованный URL появится в workflow и Settings → Pages. После публикации замените шаблонные адреса в README реальными и зафиксируйте изменение. Пока репозиторий не создан, эти адреса являются шаблонами, не работающими демо-ссылками.

## Последующие изменения

```bash
npm run check
npm run test:e2e
git add .
git commit -m "Update project"
git push
```

## Не используйте для React-проекта Live Server

Для разработки нужен `npm run dev`, а для проверки production-сборки — `npm run build` и `npm run preview`. Открытие `index.html` через `file://` или расширение Live Server не выполняет преобразование JSX и npm-импортов.

В этих проектах нет маршрутов BrowserRouter, требующих серверного fallback. Версия «до Redux» использует query-параметр, формы используют локальные вкладки. Поэтому не нужны фиктивный `404.html`, HashRouter или отдельный сервер для маршрутизации.

## Диагностика

**Белая страница / 404 ассетов.** Проверить успешность job deploy, выбрать GitHub Actions как Source, открывать адрес с `/REPOSITORY/`, не публиковать папку `src` вместо `dist`. При ручной сборке можно указать `npm run build -- --base=/REPOSITORY/`.

**Порт занят.** Завершить dev/preview через Ctrl+C или выбрать другой порт: `npm run dev -- --port 5180`. E2E по умолчанию требует 4173.

**PowerShell блокирует npm.ps1.** Использовать `npm.cmd` / `npx.cmd` или терминал Command Prompt. Менять системную политику безопасности для проекта не обязательно.

**Ошибка npm / несовместимый Node.** Проверить `node --version`, установить Node 24, перезапустить терминал VS Code, проверить сеть/прокси. Не обходить peer-зависимости с помощью `--force` или `--legacy-peer-deps` без анализа ошибки.

**Данные отличаются между dev и Pages.** localStorage привязан к origin и дополнительно разделён ключами приложения/base path. localhost, production preview и опубликованный сайт закономерно имеют разные данные. Режимы исходного и Redux-планировщиков также намеренно независимы.

Официальное руководство Vite: https://vite.dev/guide/static-deploy.html
